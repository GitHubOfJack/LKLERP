## Context

一家约50人的小公司需要一套轻量级HR管理系统，覆盖出勤、绩效、工资三个核心业务。当前痛点：出勤数据在钉钉中、绩效评分依赖Excel/纸质、工资计算靠手动操作。公司有自建Linux服务器，要求维护成本最低，无专职IT人员长期运维。第一期只做PC Web端，不做移动端应用。

系统需要处理中国特有的政策合规问题：法定节假日/调休日历、社保公积金按城市差异化配置、个税累计预扣法计算、年假按工龄分段等。

## Goals / Non-Goals

**Goals:**

- 单体应用，一键部署（Docker Compose），单台服务器运行
- 钉钉考勤数据通过 Excel/CSV 导入，第一期不做API自动同步
- 排班以默认班次为主，仅少数倒班员工需要单独排班
- 绩效采用上级打分模式，评分维度和权重可配置
- 工资自动核算，包含社保公积金和个税计算
- 员工可在PC端自助查看考勤、绩效、工资条
- 权限模型简单：超级管理员/HR/部门主管/普通员工 四级
- 所有业务参数（税率、社保比例、班次、评分维度等）可配置，不硬编码
- 站内消息通知，不依赖外部推送渠道

**Non-Goals:**

- 不做移动端应用（微信小程序/H5/APP）
- 不做微信/钉钉消息推送
- 不做自研打卡功能（GPS/指纹/人脸）
- 不做银行代发文件生成
- 不做复杂的BPM工作流引擎（单级审批即可）
- 不做多租户/多公司支持
- 不做微服务架构
- 不做API开放平台（暂不对钉钉API做自动对接）

## Decisions

### D1: 技术栈选型 —— Python + Django + Vue3

**选择**: Django + DRF（后端）、Vue3 + Ant Design Vue（前端）

**替代方案**:
- Spring Boot (Java)：开发效率低，内存占用大，一个人维护负担重
- Go + Gin：性能好但业务逻辑开发效率低，工资计算等复杂规则写起来冗长
- Node.js + NestJS：不差，但 Django Admin 开箱即用节省大量后台管理页面开发

**理由**:
- Django Admin 开箱即用，人员、部门、岗位等基础管理几乎零代码
- DRF 快速出 REST API，自带分页/过滤/认证
- Python 生态丰富（openpyxl 读写Excel、日期计算库等）
- Vue3 学习曲线低，Ant Design Vue 的表格/表单组件非常适合ERP系统
- 中文社区资源丰富，降低排障成本

### D2: 数据库 —— SQLite 优先，可平滑迁移 PostgreSQL

**选择**: 第一期使用 SQLite，架构上支持无缝切换 PostgreSQL

**替代方案**:
- 直接 PostgreSQL：更稳健，但需要额外运维数据库服务
- MySQL：与PG功能相当，但 PG 的日期函数和JSON支持更好

**理由**:
- 50人并发，SQLite 完全胜任
- SQLite 零运维，备份就是复制文件
- Django ORM 抽象层确保切换数据库时代码零改动
- 遇到性能瓶颈时再切PG，无技术债

### D3: 打卡数据源 —— Excel/CSV 导入钉钉数据

**选择**: 手动导出钉钉考勤报表 + 上传到系统导入

**替代方案**:
- 钉钉开放平台API自动同步：全自动但需要企业开发者认证，配置复杂
- 自研手机打卡：需做移动端，与PC-only策略冲突

**理由**:
- 零对接成本，第一期立即可用
- 导入格式通过列名映射配置，钉钉格式变化时改配置不改代码
- 数据模型预留API同步接口，未来升级无代码浪费
- HR每月花5分钟上传一次，可接受

### D4: 审批模型 —— 单级审批 + 自动转审

**选择**: 员工 → 直属上级审批，上级缺岗自动转上级的上级

**替代方案**:
- 多级审批链：灵活但增加复杂度，50人公司不需要
- BPM工作流引擎：过度设计

**理由**:
- 50人公司组织层级扁平，单级审批覆盖95%场景
- 自动转审处理上级请假等特殊情况，无需人工干预
- 审批记录完整保留，满足审计需求

### D5: 工资计算 —— 服务端批量计算 + 人工复核

**选择**: 每月定时汇总考勤和绩效数据，自动计算工资，HR复核确认后发放

**理由**:
- 工资计算规则复杂（社保、个税、加班费），必须自动化
- 但工资敏感度高，完全自动发风险大，必须有人工复核环节
- 支持手动调整补发，覆盖计算外特殊情况

### D6: 个税计算 —— 累计预扣法

**选择**: 严格按照中国现行《个人所得税法》累计预扣预缴方式计算

**理由**:
- 这是法定要求，不能简化
- 系统必须逐月累计计算，存储每月累计数据
- 专项附加扣除由员工自行申报、HR审核

### D7: 权限模型 —— 基于角色的简单访问控制

**选择**: 四个固定角色，基于数据范围（自己/本部门/全部）控制访问

**替代方案**:
- 完整RBAC（角色-权限-资源）：灵活但复杂，50人系统不需要
- ABAC（属性基）：过度设计

**理由**:
- 四个角色覆盖所有场景
- 数据范围控制简单直观：员工看自己，主管看本部门，HR看全部
- 代码实现简单，维护成本低

### D8: 部署架构 —— Docker Compose 单机部署

**选择**: 一台Linux服务器，Docker Compose 编排所有服务

**服务组成**:
- `web`: Django + Gunicorn（应用服务）
- `nginx`: 反向代理 + 静态文件服务
- `redis`: 缓存 + Celery broker
- `worker`: Celery 定时任务（考勤汇总、工资计算等）

**理由**:
- `docker-compose up -d` 一键部署
- 自动备份脚本 + 日志轮转 = 基本免维护
- 资源占用低，一台2C4G服务器足够支撑50人

## Risks / Trade-offs

### [风险] 钉钉导出格式变化
→ **缓解**: 导入模块使用列名映射配置（存在数据库中），而非硬编码列名。钉钉格式变化时在管理界面修改映射配置即可。

### [风险] 个税政策调整
→ **缓解**: 税率表、速算扣除数、专项附加扣除标准均做成配置项，存在数据库中。政策变化时更新配置，不改代码。

### [风险] 跨天排班的打卡归属
→ **缓解**: 夜班（如23:00-07:00）的打卡按排班日期归属，而非自然日。考勤计算时根据排班信息判断打卡记录的归属日期。

### [风险] 钉钉数据与系统员工匹配错误
→ **缓解**: 首次导入时做姓名+部门匹配，建立映射关系。后续导入自动匹配，未匹配数据标记为异常，HR人工确认后入库。

### [风险] SQLite 在高并发写入时的锁竞争
→ **缓解**: 50人系统并发写入极低（主要是HR操作），SQLite 完全胜任。预留 PostgreSQL 迁移路径，遇到瓶颈时一键切换。

### [权衡] 不做移动端意味着员工必须用电脑
→ **缓解**: 前端采用响应式设计，手机浏览器可基本访问。未来如需移动端，可基于API开发微信小程序，后端无需改动。

### [权衡] 手动导入钉钉数据有延迟
→ **缓解**: HR每月花5分钟操作，对比API对接的开发和运维成本，性价比高。预留API同步接口，需要时可升级。
